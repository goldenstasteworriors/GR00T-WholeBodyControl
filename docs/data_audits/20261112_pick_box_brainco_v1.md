## 结论

文件结构和数值完整，图像与表格的帧序号一致；但不能据此认定曝光、状态和动作严格同步。图像运动与机器人姿态变化的对比支持图像约晚1～3个录制帧，整体最佳估计为2帧，即名义40ms。该数值是未标定的运动相关性估计，不是硬件时间戳测量，不应直接作为全数据集固定平移量。

视频主要朝向地面，手部经常只在边缘或画面外；抽帧概览未显示完整的抓取盒子过程。这条数据适合检查采集链路，尚不宜作为经过验收的“成功抓盒子”视觉示范。

## 相机与状态/动作对齐

分析方法：对全部视频帧计算低分辨率背景光流，用RANSAC拟合全局图像运动；根据记录的基座四元数和29维关节状态，通过项目原G1模型的FK得到torso姿态。对接近重复的图像按更新间隔累计机器人角运动，再扫描两者的帧偏移。未使用相机外参标定，因此用线性拟合吸收几何差异。

| 数据范围 | 水平/垂直/画面旋转三个信号的最佳偏移 |
| --- | --- |
| 全episode | 图像均晚2帧；名义40ms |
| 帧0～349 | 图像晚3 / 2 / 3帧 |
| 帧350～699 | 图像均晚2帧 |
| 帧700～1026 | 图像晚1 / 2 / 1帧 |

全段三个通道的最佳拟合R²分别约0.785、0.777、0.737；零偏移时约0.687、0.519、0.653。结果支持“小幅且可能变化的图像滞后”，未发现需要以秒为单位整体挪动视频的证据。这里每帧20ms来自文件的名义时间轴，无法核实实际采集间隔是否始终20ms。

相邻解码图像平均灰度差小于0.3的比例为48.1%，按此启发式约有534次独立图像变化，折合名义26次/秒；最长连续近似不变区间为6帧，名义120ms。H.264重编码会改变像素，故严格逐像素相同的相邻帧为0。这些数字不能直接当作硬件曝光帧率或丢帧率；静止场景也会影响近重复判定。相机默认30fps、记录容器50fps本就允许重用图像，视频标注50fps不等于50次独立曝光。

手指命令阶跃到手部平均位置完成该次变化50%的时间，中位约280ms，范围140～360ms（只统计下一次命令前达到阈值的事件）。这是命令→执行机构→状态反馈的响应，不能全部归因于相机不同步，也不应为让曲线重合而把action直接平移280ms。

对应的SMPL帧序号变为0，人体根四元数回退到单位四元数。源码会在SMPL消息超过100ms未更新时填写这些回退值，符合本次数据表现；仅凭文件无法进一步区分头显、网络或PC调度造成的停更。使用SMPL作为训练目标时需要标记这些行，不能把零姿态当作真实动作。

整条teleop.stream_mode为1（POSE）。VR三点及planner专属字段全零/默认值符合该模式的导出逻辑，不单独判为采集故障。

## 对齐精度限制与建议

当前Parquet未保存每帧的相机曝光/源帧时间戳、相机帧号，以及身体状态/动作源时间戳。采集端分别取“最新图像”和“最新状态”，没有按源时间配对或插值；保存端再按帧序号生成50Hz时间轴。因此帧数一致、PTS一致和timestamp均匀都不能证明实际严格同步，也无法用现有文件准确恢复所有原始停顿时长。

下一次正式采集应保留这些源时间/帧号及PC单调接收时间，核对时钟关系后再做时间配对。本次不改采集代码、不修改现有数据、不自动执行固定帧移位或SMPL插值。
